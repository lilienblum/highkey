# Highkey

- Use Bun for JavaScript commands, including `bun run fmt`, `bun typecheck`, `bun lint`, and `bun test`. Do not use npm or Node.
- `apps/ingest` is the Rust ingest app: it only receives events and logs (`/api/ingest`, `/api/logs/ingest`, `/api/logs/v1/logs`) and serves `/tracker.js`. It is stateless and changes rarely, so it knows nothing about the app. `apps/app` is TanStack Start on Bun and owns everything else: projects, sources, keys, queries, dashboards, saved views, MCP and live hints, with management state in SQLite. Events and logs live in self-hosted ClickHouse; they are separate signals with separate keys, tables and retention. Highkey has its own accounts on Better Auth (the app's `/api/auth`): people belong to organizations with roles (owner, admin, member, viewer), organizations own projects, and every `/api` request resolves an actor (session, `hk_` API key, or an agent's OAuth token on `/mcp`) scoped to one organization, with its role read on each request (`server/auth/actor.ts`, `server/api/router.ts`). Routes state their permission; a project in the path is looked up inside the actor's organization. Keep public ingestion keys (`pk_`, `pl_`) separate from API keys. Keep blocking database work off Tokio HTTP workers.
- The two apps share only ClickHouse: the dashboard owns the migrations (`clickhouse/migrations`) and mirrors keys into `highkey.ingest_keys`; the ingest app checks `highkey.ingest_contract` at start. Change that contract expand-then-contract: add what the new ingest app needs first, and remove what the old one used only after it is gone.
- Keep ingestion acknowledgments after commit, bounded queues, product-scoped deduplication (exact for 24 hours, the first copy wins), and typed properties intact. One ingest process per deployment, because exact dedup relies on it.
- Every project reads ClickHouse as its own user, through `SQL SECURITY DEFINER` views that hold only its rows. Dashboard documents never carry SQL: queries are events, logs, funnel or retention entities.
- Run `bun run fmt` (bare `bun fmt` runs Bun's built-in formatter), `bun typecheck`, `bun lint`, `bun run test` (bare `bun test` covers only `sdk/`; start its ClickHouse once with `bun scripts/clickhouse.ts test-up`), `bun run build`, `cargo test`, and `cargo clippy --all-targets --all-features -- -D warnings` for relevant changes. Run `bun run test:e2e` for UI changes and `bun run test:load` for ingest or storage changes.
- Dashboard primitives use shadcn/ui on Base UI (`@base-ui/react`), with Hugeicons and the local single-theme Kanagawa Wave styles (orange primary, yellow/violet/aqua data accents). Keep `components.json` on `base-vega`; use `render` composition, not Radix or `asChild`. Preserve keyboard/focus behavior, SSR labels, and stable refresh geometry.
- Custom dashboards are dashboard-owned `highkey.dashboard/v1` documents, written by agents over MCP, never edited by hand in the dashboard UI. `/api/read/*` is the only CORS surface (loopback plus `HIGHKEY_CORS_ORIGINS`), and it needs an API key. MCP is served by the dashboard: `/mcp` (shown to users; `/api/mcp`) takes OAuth tokens and API keys, `/api/read/mcp` API keys only; neither takes a browser session.
- MIT license. Keep documentation and collection examples aligned with API changes.
- For app UI work, read `apps/app/PRODUCT.md` and `apps/app/DESIGN.md`; the normative design sidecar is `apps/app/.impeccable/design.json`.

- Highkey runs as two native Tako apps only (root `tako.ingest.toml` and `tako.app.toml`); there is no Docker Compose or Docker image. Locally ClickHouse runs in Docker (`bun scripts/clickhouse.ts dev-up`); in production it is a ClickHouse server installed on the host with Highkey's `deploy/clickhouse` settings. `bun run dev:standalone` runs the same apps without Tako. Keep Tako itself unchanged. The ingest app's post-commit webhook hints and the app's own writes feed the app's ephemeral channel; never place raw events or credentials in channel messages. The app's management state lives in a Tako database bound as `main` (named `highkey`), with its schema in the numbered SQL files of `migrations/` (add-only; never edit an applied file); without Tako it is a bun:sqlite file migrated by the app. All store access goes through the async `Db` interface (`apps/app/src/server/db/db.ts`); transactions never await ClickHouse or the network (Tako rolls back a transaction idle for 10 s). Background work (the minute reconcile) is a Tako workflow under `apps/app/src/workflows/`. The ingest app holds no state.
